# Практическая работа №5. Межсервисное взаимодействие

## Цель работы

Закрепление практических навыков организации межсервисного взаимодействия: работа с брокером сообщений RabbitMQ и отправка асинхронных сообщений между программами.

Задание 1 методических указаний выполняется по индивидуальным вариантам. Варианты считаются как остаток от деления последней цифры студенческого билета на количество вариантов (остаток 0 — последний вариант); так как внутри команды варианты не должны повторяться. По номерам билетов получились варианты: Расулов (23Л1393) — 3, Измайлов (23и1013) — 3, Агзамов (23и0808) — 4, Олефиров (23И1114) — 4. Повторы разрешены по взаимной договорённости: Измайлов взял вариант 1, Олефиров — вариант 2, так что в команде заняты все четыре варианта. Параметры вариантов приведены в таблице 1.

Таблица 1 — Параметры индивидуальных вариантов

| Вариант | Тип очереди | Тип обменника | Способ определения задержки (секунды) |
| --- | --- | --- | --- |
| 1 | Авто-удаляемая | Topic | Количество точек в теле сообщения |

## Структура решения

Каждый участник реализовал собственное решение в отдельной папке pr5-rabbitmq/<фамилия>/, состоящей из трёх файлов: common.py (параметры варианта и подключение), producer.py (поставщик) и consumer.py (потребитель). Параметры варианта заданы константами в common.py, вариант аргументом не выбирается. Имя очереди имеет формат <группа>_<фамилия> (ikbo-65-23_<фамилия>), обменник называется ikbo-65-23_<фамилия>_exchange, поэтому работы четырёх участников не пересекаются на одном брокере. Параметры брокера берутся из переменных окружения, по умолчанию — учебный сервер.

Схема взаимодействия во всех вариантах одна и та же: поставщик (P) публикует сообщение в обменник (X), обменник по правилу привязки направляет его в именованную очередь, из которой сообщение забирает потребитель (C). Обменник и очередь объявляются с обеих сторон: нет гарантии, что потребитель будет запущен после поставщика, а объявление существующего объекта с теми же параметрами брокер игнорирует.

## Задание 2. Сообщения, на которые реагируют сервисы

Для всех восьми сервисов платформы определены асинхронные сообщения из модели ПР4. Все они публикуются в единый обменник gamehub, а каждый сервис-подписчик создаёт собственную очередь на каждый нужный ключ.

Настройки обменника и очередей одинаковы для всех сообщений. Обменник: имя gamehub, тип topic, durable=True. Очереди: durable=True, имя в формате gamehub_<сервис>_<ключ маршрутизации с символом «_» вместо точки>, привязка — точный ключ сообщения. Сообщения публикуются как persistent (delivery_mode=2) в формате JSON (UTF-8). Подписчик использует prefetch_count=10 и ручное подтверждение: ack — после успешной обработки, nack — при ошибке. Обработчики идемпотентны: повторная доставка сообщения не приводит к повторному эффекту (например, оплата по одному заказу создаётся один раз).

## Вывод

Реализована простейшая схема обмена сообщениями «поставщик — обменник — очередь — потребитель» для всех четырёх вариантов методических указаний: авто-удаляемая и сохраняемая очереди, обменники topic, direct и fanout, четыре способа имитации нагрузки. Варианты распределены в команде без повторов: Расулов — 3, Измайлов — 1, Агзамов — 4, Олефиров — 2. Проверка на локальном брокере показала, что авто-удаляемая очередь исчезает вместе с потребителем, durable-очередь с persistent-сообщениями и durable-обменник переживают перезапуск брокера, а при prefetch_count=1 и ручном подтверждении потребитель не получает новое сообщение, пока не закончил предыдущее. В задании 2 описаны все асинхронные сообщения платформы: структура тела, выполняемый функционал, настройки обменника и очередей; эти сообщения реализуются в ПР7.
