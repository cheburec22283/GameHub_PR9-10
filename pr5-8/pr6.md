# Практическая работа №6. Проектирование REST API

## Цель работы

Изучить основные методы синхронного взаимодействия между сервисами, а также получить практические навыки проектирования REST API.

## Анализ функций

В ПР7 реализованы все восемь сервисов из ПР4: user-service, publisher-service, catalog-service, license-service, order-service, payment-service, library-service и review-service. Каждый участник команды проектирует API двух собственных сервисов (минимум по методическим указаниям); распределение приведено в таблице 4. Между сервисами определены четыре синхронные связи (Sync REST: publisher → user, catalog → publisher, order → license, review → order) — по одной у каждого участника — и асинхронные связи через RabbitMQ (сообщения описаны в ПР5, задание 2).

## Общие соглашения

- Методы HTTP: GET — получение, POST — создание, PUT — полная замена объекта. Удаление объектов не предусмотрено: платформа хранит историю, поэтому вместо DELETE используются смены статуса (блокировка, снятие с публикации, аннулирование), поэтому PATCH и DELETE не применяются.

- Действия, которые не укладываются в CRUD (отменить, активировать, заблокировать), оформлены как пользовательские операции: после ресурса через двоеточие указывается действие, метод POST (например, POST /api/orders/{id}:cancel).

- Идентификаторы — UUID (строка). Денежные суммы передаются строкой с двумя знаками после точки, чтобы не терять точность. Даты — строка ISO 8601 в UTC.

- Все списки поддерживают пагинацию переменными запроса offset (целое ≥ 0, отступ от начала списка, по умолчанию 0) и count (целое от 1 до 100, размер страницы, по умолчанию 20) и сортируются по дате создания; все переменные фильтрации и пагинации необязательны.

- Авторизация в учебной версии не реализуется; в боевой версии идентификатор пользователя передавался бы в заголовке Authorization: Bearer <token> и проверялся через user-service. В описании методов указана роль, которой метод предназначен.

- Коды ответов: 200/201 — успех, 400 — некорректные данные, 404 — объект не найден, 409 — действие недопустимо в текущем состоянии объекта, 422 — ошибка валидации тела или параметров, 503 — недоступен зависимый сервис.

## user-service (Расулов Р.Б.)

### 1. Регистрация пользователя

Path: /api/users

Тип запроса: POST

Авторизация: не требуется

Параметры запроса: отсутствуют

Структура тела запроса:

- email — строка-адрес, уникальный адрес электронной почты;

- name — строка, имя пользователя, непустое;

- role — строка, buyer (по умолчанию) или publisher; роль admin при регистрации недопустима;

Пример тела запроса:

```text
{"email": "ruslan@example.com", "name": "Руслан", "role": "buyer"}
```


Пример ответа (201 Created): объект User (см. описание сущностей), is_blocked = false. Публикуется сообщение user.registered.

Ошибки: 409 — email уже занят или запрошена роль admin; 422 — некорректный email.

### 2. Получение списка пользователей

Path: /api/users

Тип запроса: GET

Авторизация: администратор

Параметры запроса (все необязательные):

- role — строка, фильтр по роли: buyer, publisher или admin;

- offset — целое ≥ 0, отступ от начала списка, по умолчанию 0;

- count — целое от 1 до 100, размер страницы, по умолчанию 20;

Структура тела запроса: отсутствует

Пример ответа (200 OK): массив объектов User, отсортированных по дате регистрации.

### 3. Получение пользователя по id

Path: /api/users/{user_id}

Тип запроса: GET

Авторизация: не требуется

Параметры запроса:

- user_id — UUID (параметр пути), идентификатор пользователя;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект User. Метод вызывается синхронно из publisher-service при создании издателя.

Ошибки: 404 — пользователя нет.

### 4. Блокировка пользователя

Path: /api/users/{user_id}:block

Тип запроса: POST

Авторизация: администратор

Параметры запроса:

- user_id — UUID (параметр пути), идентификатор блокируемого пользователя;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект User с is_blocked = true. Публикуется сообщение user.blocked.

Ошибки: 404 — нет пользователя; 409 — пользователь уже заблокирован или является администратором.

## publisher-service (Расулов Р.Б.)

### 1. Создание профиля издателя

Path: /api/publishers

Тип запроса: POST

Авторизация: издатель

Параметры запроса: отсутствуют

Структура тела запроса:

- owner_id — UUID, идентификатор пользователя-владельца;

- name — строка, название студии или издателя, непустое;

Пример тела запроса:

```text
{"owner_id": "5d1e9c0a-2b7f-4f3e-9a41-0f6c1d2b8e77", "name": "Nova Games"}
```


Перед созданием сервис синхронно запрашивает user-service (GET /api/users/{owner_id}): владелец должен существовать, иметь роль publisher и не быть заблокированным. Профиль создаётся в статусе pending и ожидает верификации.

Пример ответа (201 Created): объект Publisher со статусом pending. Публикуется сообщение publisher.created.

Ошибки: 409 — владелец не найден, не является издателем или заблокирован, либо у владельца уже есть издатель с таким названием; 503 — user-service недоступен.

### 2. Получение списка издателей

Path: /api/publishers

Тип запроса: GET

Авторизация: не требуется

Параметры запроса (все необязательные):

- status — строка, фильтр по статусу: pending, verified или blocked;

- owner_id — UUID, фильтр по владельцу;

- offset — целое ≥ 0, отступ от начала списка, по умолчанию 0;

- count — целое от 1 до 100, размер страницы, по умолчанию 20;

Структура тела запроса: отсутствует

Пример ответа (200 OK): массив объектов Publisher.

### 3. Получение издателя по id

Path: /api/publishers/{publisher_id}

Тип запроса: GET

Авторизация: не требуется

Параметры запроса:

- publisher_id — UUID (параметр пути), идентификатор издателя;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект Publisher. Метод вызывается синхронно из catalog-service при публикации игры.

Ошибки: 404 — издателя нет.

### 4. Верификация издателя

Path: /api/publishers/{publisher_id}:verify

Тип запроса: POST

Авторизация: администратор

Параметры запроса:

- publisher_id — UUID (параметр пути), идентификатор издателя;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект Publisher со статусом verified (переход pending → verified). Публикуется сообщение publisher.verified.

Ошибки: 404 — нет издателя; 409 — издатель уже верифицирован или заблокирован.

### 5. Блокировка издателя

Path: /api/publishers/{publisher_id}:block

Тип запроса: POST

Авторизация: администратор

Параметры запроса:

- publisher_id — UUID (параметр пути), идентификатор издателя;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект Publisher со статусом blocked (допустимо из pending и verified). Публикуется сообщение publisher.blocked, по которому catalog-service снимает с публикации все игры издателя.

Ошибки: 404 — нет издателя; 409 — издатель уже заблокирован.

## catalog-service (Измайлов Б.А.)

### 1. Публикация игры

Path: /api/games

Тип запроса: POST

Авторизация: издатель

Параметры запроса: отсутствуют

Структура тела запроса:

- publisher_id — UUID, идентификатор издателя;

- title — строка, название игры, непустое;

- genre — строка, жанр;

- description — строка, описание, непустое;

- platforms — массив строк (не менее одной), поддерживаемые платформы: windows, linux, macos;

- min_requirements — строка, необязательная, минимальные системные требования;

Пример тела запроса:

```text
{
  "publisher_id": "9b2f1c4e-1111-4a2a-8201-537cdff25fed",
  "title": "Звёздный рубеж",
  "genre": "Космическая стратегия",
  "description": "Пошаговая стратегия о колонизации галактики",
  "platforms": ["windows", "linux"],
  "min_requirements": "CPU 4 ядра, 8 ГБ ОЗУ, 20 ГБ на диске"
}
```


Перед созданием сервис синхронно запрашивает publisher-service (GET /api/publishers/{publisher_id}): издатель должен существовать и иметь статус verified.

Пример ответа (201 Created): объект Game со статусом published. Публикуется сообщение catalog.game_published.

Ошибки: 409 — издатель не найден или не верифицирован; 503 — publisher-service недоступен.

### 2. Поиск по каталогу

Path: /api/games

Тип запроса: GET

Авторизация: не требуется

Параметры запроса (все необязательные):

- q — строка, часть названия, без учёта регистра;

- genre — строка, жанр;

- platform — строка, платформа из списка поддерживаемых, без учёта регистра;

- publisher_id — UUID, фильтр по издателю;

- offset — целое ≥ 0, отступ от начала списка, по умолчанию 0;

- count — целое от 1 до 100, размер страницы, по умолчанию 20;

Структура тела запроса: отсутствует

Пример ответа (200 OK): массив объектов Game; в выдаче только карточки со статусом published. Пример: GET /api/games?q=рубеж&platform=windows&offset=0&count=20.

### 3. Получение игры по id

Path: /api/games/{game_id}

Тип запроса: GET

Авторизация: не требуется

Параметры запроса:

- game_id — UUID (параметр пути), идентификатор игры;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект Game (в том числе снятый с публикации).

Ошибки: 404 — игры нет.

### 4. Снятие игры с публикации

Path: /api/games/{game_id}:unpublish

Тип запроса: POST

Авторизация: издатель

Параметры запроса:

- game_id — UUID (параметр пути), идентификатор игры;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект Game со статусом unpublished. Публикуется сообщение catalog.game_unpublished. Тот же переход выполняется автоматически для всех игр издателя по сообщению publisher.blocked.

Ошибки: 404 — нет игры; 409 — игра уже снята с публикации.

## license-service (Измайлов Б.А.)

Сервис хранит пул лицензионных ключей по каждой игре: сколько ключей загружено издателем, сколько закреплено за заказами и по какой цене они продаются.

### 1. Получение списка наличия ключей

Path: /api/licenses

Тип запроса: GET

Авторизация: не требуется

Параметры запроса (все необязательные):

- publisher_id — UUID, фильтр по издателю;

- offset — целое ≥ 0, отступ от начала списка, по умолчанию 0;

- count — целое от 1 до 100, размер страницы, по умолчанию 20;

Структура тела запроса: отсутствует

Пример ответа (200 OK): массив объектов License: quantity — всего ключей в пуле, reserved — закреплено за заказами, available = quantity − reserved (вычисляемое поле).

### 2. Получение наличия ключей по игре

Path: /api/licenses/{game_id}

Тип запроса: GET

Авторизация: не требуется

Параметры запроса:

- game_id — UUID (параметр пути), идентификатор игры;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект License. Метод вызывается синхронно из order-service при оформлении заказа.

Ошибки: 404 — игра не заведена.

### 3. Обновление наличия ключей

Path: /api/licenses/{game_id}

Тип запроса: PUT

Авторизация: издатель

Параметры запроса:

- game_id — UUID (параметр пути), идентификатор игры;

Структура тела запроса:

- publisher_id — UUID, идентификатор издателя;

- price — строка-число > 0, цена за один ключ;

- quantity — целое ≥ 0, общее количество ключей;

Пример тела запроса:

```text
{"publisher_id": "9b2f1c4e-1111-4a2a-8201-537cdff25fed", "price": "1999.00", "quantity": 10}
```


Объект передаётся целиком (метод PUT): запись создаётся или заменяется.

Пример ответа (200 OK): объект License.

Авторизация: издатель, администратор

Параметры запроса (все необязательные):

- count — целое от 1 до 100, размер страницы, по умолчанию 20;

Структура тела запроса: отсутствует

Пример ответа (200 OK):

```text

  "game_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "quantity": 1, "status": "active"}]
```

### Длительная операция: импорт пакета ключей

Массовая загрузка пакета ключей издателя (десятки тысяч строк) может выполняться минутами, поэтому она оформлена по схеме длительной операции (рисунок 6.3 методических указаний): клиент запускает операцию, получает её идентификатор и периодически опрашивает статус. Операция спроектирована, но в ПР7 не реализована; задача ставится в очередь RabbitMQ (по схеме ПР5).

Запуск: Path: /api/key-batches:import · Тип запроса: POST · Авторизация: издатель · Параметры запроса: отсутствуют.

Структура тела запроса:

- publisher_id — UUID, издатель;

- game_id — UUID, игра, для которой загружаются ключи;

- file_url — строка, ссылка на CSV-файл с ключами.

Пример ответа (202 Accepted):

```text
{"operation_id": "d41f7b9c-0a6e-4c23-95b8-3e5a7c1d9f02", "is_finished": false}
```


Опрос статуса: Path: /api/operations/{operation_id} · Тип запроса: GET · Авторизация: издатель · Параметр пути operation_id — UUID операции. Пока идёт импорт:

```text
{"operation_id": "d41f7b9c-0a6e-4c23-95b8-3e5a7c1d9f02", "is_finished": false, "progress": 40}
```


После завершения:

```text
{"operation_id": "d41f7b9c-0a6e-4c23-95b8-3e5a7c1d9f02", "is_finished": true,
 "result": {"imported": 15200, "failed": 3, "errors_url": "https://files.example.com/errors/d41f7b9c.csv"}}
```


## order-service (Агзамов И.И.)

### 1. Создание заказа

Path: /api/orders

Тип запроса: POST

Авторизация: покупатель

Параметры запроса: отсутствуют

Структура тела запроса:

- customer_id — UUID, идентификатор покупателя;

- items — массив позиций (не менее одной), состав заказа;

- items[].game_id — UUID, идентификатор игры;

- items[].quantity — целое от 1 до 5, количество копий (например, в подарок);

Пример тела запроса:

```text
{
  "customer_id": "85db966c-67f1-411e-95c0-f02edfa5464a",
  "items": [
    {"game_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "quantity": 1}
  ]
}
```


Цены в запросе не передаются: сервис синхронно запрашивает license-service (GET /api/licenses/{game_id}) и берёт цену и наличие оттуда, чтобы покупатель не мог подменить цену. Одинаковые позиции объединяются. После создания публикуется сообщение order.created.

Пример ответа (201 Created): объект Order со статусом created; цена в позициях зафиксирована на момент заказа.

Ошибки: 400 — игра не найдена или свободных ключей недостаточно; 503 — license-service недоступен.

### 2. Получение списка заказов

Path: /api/orders

Тип запроса: GET

Авторизация: покупатель (свои заказы), администратор

Параметры запроса (все необязательные):

- customer_id — UUID, фильтр по покупателю;

- status — строка, фильтр по статусу: created, confirmed, completed, canceled;

- offset — целое ≥ 0, отступ от начала списка, по умолчанию 0;

- count — целое от 1 до 100, размер страницы, по умолчанию 20;

Структура тела запроса: отсутствует

Пример ответа (200 OK): массив объектов Order. Пример: GET /api/orders?customer_id=85db966c-…&status=created&offset=0&count=20.

### 3. Получение заказа по id

Path: /api/orders/{order_id}

Тип запроса: GET

Авторизация: покупатель, администратор

Параметры запроса:

- order_id — UUID (параметр пути), идентификатор заказа;

Структура тела запроса: отсутствует

Пример ответа (200 OK): объект Order. Метод вызывается синхронно из review-service при создании отзыва.

Ошибки: 404 — заказа нет.

### 4. Отмена заказа

Path: /api/orders/{order_id}:cancel

Тип запроса: POST

Авторизация: покупатель

Параметры запроса:

- order_id — UUID (параметр пути), идентификатор заказа;

Структура тела запроса:

- reason — строка, необязательная, причина отмены;

Пример тела запроса:

```text
{"reason": "Передумал покупать"}
```


Допустима из статусов created и confirmed — пока ключ не выдан в библиотеку. Публикуется сообщение order.canceled с флагом refund_required (заказ был оплачен): license-service снимает резерв, payment-service оформляет возврат.

Пример ответа (200 OK): объект Order со статусом canceled.

Ошибки: 404 — нет заказа; 409 — заказ уже завершён или отменён.

Жизненный цикл заказа: created → confirmed (оплата) → completed (ключ выдан в библиотеку); из created и confirmed возможен переход в canceled. Сборки и физической доставки у цифрового товара нет: после подтверждения оплаты ключ выдаётся автоматически.
